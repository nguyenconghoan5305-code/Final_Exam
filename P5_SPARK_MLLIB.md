# P5.1 Spark MLlib development-fold demonstration

## Scope and frozen contract

The examination PDF, page 2 Part 5, asks for a short Spark MLlib demo alongside the baseline and substantive model comparison. This implementation is a separate demonstration. The development-only scikit-learn selection remains `bounded_hist_gradient_boosting` from `dev20261121a` and `dev20261121b`; Spark does not reopen that selection.

`src/bft65b/modelling/spark_demo.py` uses the accepted `split20261120b` assignments, `featuretable20261120a` seven-feature model table, both accepted development runs, and `p44audit20261120a`. It fixes **fold_3** before fitting: train Q 1984Q1–2007Q4, exclude 2008Q1–2008Q4, validate Q 2009Q1–2012Q4. The accepted plan expects 1,173,760 training bank-quarters (7,799 positive rows; 1,999 distinct positive events) and 122,293 validation bank-quarters (1,521 positive rows; 442 distinct positive banks/events). The 96 training and 16 validation Parquet paths are selected directly from the accepted frozen plan. The 2013 outer gap and the 2014Q1–2025Q2 test predictor partitions are never opened. Complete `(CERT,Q,Y)` relations are compared to the accepted split assignments before fitting; no outcome-selected sample is used.

The predictor vector contains, in the accepted order, `asset_size`, `equity_to_assets_pct`, `deposits_to_assets_pct`, `roa_reported_pct`, `pca_leverage_reported_pct`, `asset_growth_qoq_pct`, and `roa_four_quarter_mean_pct`. `CERT`, `Q`, `Y` and all event/cohort/audit fields are excluded from the vector. Decimals and doubles are converted to Spark `DoubleType` for MLlib; the Parquet source retains its original precision. Nonfinite values are rejected. Nulls are filled from Spark `approxQuantile([0.5], relativeError=0.001)` computed on **training only**. A training column with no observed values receives a fixed zero fill and remains in the seven-dimensional vector. This fill is a model-input convention, not a change to source data.

The fixed MLlib `Pipeline` has `VectorAssembler`, `StandardScaler(withMean=True, withStd=True)`, and `LogisticRegression(maxIter=20, regParam=0.1, elasticNetParam=0, tol=1e-6, fitIntercept=True, standardization=False)`. The Spark scaler uses its own standard-deviation convention; its estimated center and scale are recorded. This differs from scikit-learn's exact median `SimpleImputer`, population-variance `StandardScaler`, liblinear logistic baseline, and selected histogram gradient boosting. The Spark classifier is intentionally a simple demonstration; no probability or parameter equivalence is assumed. No class weights, resampling, calibration, threshold or candidate search are used.

The local runtime is the previously verified Python 3.11.9 / Java 17.0.21 / Spark 3.5.7 host, using existing ignored native Hadoop files whose recorded SHA-256 values are checked before each run. Frozen settings are `local[2]`, eight shuffle partitions, adaptive execution off, UTC session timezone, UI off and 4 GB driver heap. The run summary records effective runtime settings, native-library status, input partition counts, training medians/scaler statistics, metrics and timings. The fit timer wraps `Pipeline.fit`; the validation timer includes `transform` and a full `collect` of every score, so lazy Spark inference is materialized. Input verification, startup, reporting and saved-output checks are recorded separately and are not a benchmark against pandas or Polars. Physical plans are saved before and after validation materialization.

`sklearn.metrics.average_precision_score` on **saved Spark validation labels and scores** provides the same stepwise AP definition as the accepted development comparison. ROC-AUC and Brier score are descriptive secondary metrics. Spark `areaUnderPR` is not relabelled as that AP. Scores are observation-level and one FDIC failure may label multiple prediction quarters. This single local run cannot establish cluster speedup or future test performance.

## Reproducibility and acceptance

Use the exact process-local PowerShell environment in the README Task 3.0 section. `tests/spark_runtime_acceptance.py` must pass first. Then run with fresh IDs:

```powershell
.\.venv_local\Scripts\python.exe -B -m bft65b.modelling.spark_demo run --project-root C:\NEU\BFT65B --run-id sparkdemo_new_a
.\.venv_local\Scripts\python.exe -B -m bft65b.modelling.spark_demo verify --project-root C:\NEU\BFT65B --run-id sparkdemo_new_a
.\.venv_local\Scripts\python.exe -B -m bft65b.modelling.spark_demo run --project-root C:\NEU\BFT65B --run-id sparkdemo_new_b
.\.venv_local\Scripts\python.exe -B -m bft65b.modelling.spark_demo compare --project-root C:\NEU\BFT65B --run-id sparkdemo_new_a --compare-run-id sparkdemo_new_b
```

Each run writes a fresh ignored `runs/task_5_3_spark_mllib/<run-id>/` evidence directory and `data_processed/task_5_3_spark_mllib/<run-id>/validation_scores.parquet`. Manifest status must be complete, all recorded validations must pass, and independent read-back must confirm schema, ZSTD codec, keys, class counts, finite bounded scores, metrics, input hashes and file checksum. Repeat comparison requires exact key/label coverage and a predeclared maximum absolute score difference of `1e-8`; it does not expand the tolerance to hide a mismatch.

Both fresh runs, `sparkdemo20261122a` and `sparkdemo20261122b`, passed independent saved-output verification. The runtime synthetic gate on this host passed DataFrame transformation, Spark Parquet write/read, PyArrow-to-Spark date/decimal/null/key parity, and MLlib fit/transform; the complete log is ignored at `tmp/spark_p53_acceptance.log`. Its preprocessing, regularization and optimizer differ from the accepted scikit-learn candidates; it does not supersede the selected `bounded_hist_gradient_boosting`, and no threshold or test score was computed.
